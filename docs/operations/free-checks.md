# Free checks and manual paid access

Each free (trial) account receives a **lifetime allowance of single-part CAD checks**, sized by email domain (`backend/src/auth/email_tiers.py`): **15** for a work address (`FREE_CHECKS_WORK`) and **3** for a consumer mailbox such as Gmail or Outlook (`FREE_CHECKS_PERSONAL`). Accounts created before email tiers keep their recorded `users.free_check_grant` (10) when it is larger. Pro accounts get `PRO_MONTHLY_CHECKS` (default 50) per Stripe billing period; pilot accounts are unlimited.

A check means a part: one file's preview, DFM analysis and cost estimate. The file is identified by its hash (filename and bytes). The first completed analysis or estimate of a file consumes one check; re-running any step on the same file later (another material, quantity, machine set or service conditions) reuses that file's check and never counts again, even after the allowance is spent. A different file is a different check. Failed operations can retry; invalid files do not consume completed checks. Simultaneous requests reserve slots before compute, so they cannot exceed the allowance by racing. API keys and browser sessions share the account allowance.

**The sample part never uses a check.** The in-app sample ("Run the sample", the routing bracket generated by `frontend/src/lib/verify/sample-cad.ts`) is recognised on the server by the SHA-256 of its exact bytes (`SAMPLE_PART_SHA256` in `backend/src/auth/validation_caps.py`), never by a client flag. It runs on the real engine on every plan, even with the allowance spent, and records no check. A copy changed by one byte is an ordinary upload and counts like one. If the sample generator changes, update the hash; `test_the_sample_hash_is_the_app_sample_bracket` and `frontend/src/lib/verify/sample-cad.test.ts` fail until both sides agree.

The public `/sample` is a recorded example with no live computation. Both legacy `/validate/demo` endpoints require authentication and use the same allowance.

## Tools on every plan

ScaleCAD's own fixes (`POST /api/v1/parts/{hash}/fixes/{fix}`), mesh repair (`POST /api/v1/validate/repair`), Fit in context (`POST /api/v1/validate/fit`) and Design Studio (`POST /api/v1/designs`, `/designs/interpret`, `/designs/{id}/revisions`) are on every plan, the free trial included (product owner decision, 2026-10-21). None of them uses a check. Every other protection stays: authentication and roles, organization scoping, the kill switch, admission control, each route's own per-user rate limit, and each tool's size and time limits.

Free accounts also have a per-user ceiling on the expensive ones (`backend/src/auth/free_tool_limits.py`), counted across all their parts and stored with the rate limiter (Redis). Over the ceiling the API answers `429` with `detail.code = "free_tool_limit"`, a plain message and `Retry-After`. Pro and pilot accounts keep only the route limits.

| Tool | Setting | Default for free accounts |
|---|---|---|
| ScaleCAD's fixes | `FREE_FIX_LIMIT` | 10 an hour, 40 a day |
| Mesh repair | `FREE_REPAIR_LIMIT` | 10 an hour, 40 a day |
| Fit in context | `FREE_FIT_LIMIT` | 10 an hour, 40 a day |
| Fit in assembly 3D previews | `FREE_FIT_PREVIEW_LIMIT` | 20 an hour, 80 a day |
| Design Studio generation (design or revision) | `FREE_DESIGN_LIMIT` | 20 an hour, 60 a day |

Reading a Studio prompt is a local parse and has only its route limit. Fit in assembly's 3D previews (`POST /validate/preview-mesh?purpose=fit`) reserve no check; they are refused (404) while the server doesn't offer Fit (`CONTEXT_FIT_ENABLED`), and free accounts have their own ceiling on them (`FREE_FIT_PREVIEW_LIMIT`, 20 an hour and 80 a day; two per pair). Measuring the fit uses no check.

**Copies ScaleCAD makes never use another check.** A fix or a mesh repair writes a `derived-from.json` record next to the copy's stored source in the organization's store. When a copy's exact bytes come back (keeping a repaired copy, re-checking a downloaded fixed file), the server finds that record and, if the parent is a part checked in the same organization, runs every step without taking or recording a check. Nothing the browser sends can claim it; a copy changed by one byte is an ordinary upload.

**Mesh repair of an uploaded file** (`POST /validate/repair`) is free for a part the account already checked (the same file, or the same bytes under another name) and records no run. A file the account never checked comes back with its full check (the repair runs the analysis on the original), so it takes one check like an upload, once; with the allowance spent it is refused like any new file. Repair of a kept part (`POST /parts/{hash}/repair`) never uses a check.

## Tools that still need approved access

These still require the pilot entitlement (`require_paid_access`, `403 paid_access_required`): batch runs, BOM assembly ingest, multi-part assembly analysis and the assembly 3D view, SAM-3D segmentation, direct multipart bulk uploads, photo-to-3D reconstruction and recalibration from ground truth. Reading saved results and exporting existing reports remain available after the free allowance is exhausted.

## Giving an account more checks

There is no admin screen for this. An authorized operator with database access uses one of two tools for the verified account:

- **The plan: `backend/scripts/set_plan.py`.** Don't set `users.plan` by hand. The script sets it, prints the account before and after, and writes a `user.plan_changed` audit row (actor `staff script`, with from, to and your reason) in the same transaction, so the organization's Activity shows "Plan changed · Free trial → Pilot". The same plan again changes nothing and writes nothing. It is a command, never a web route.

  ```
  cd backend
  DATABASE_URL=postgresql://… python -m scripts.set_plan \
      --email dana@northfieldpumps.com --plan pilot \
      --reason "Pilot agreed with Northfield Pumps, 2026-10-22"

  Before: account 52 dana@northfieldpumps.com · plan trial · organization 01M5H5… · no Stripe subscription
  After:  account 52 dana@northfieldpumps.com · plan pilot · organization 01M5H5… · no Stripe subscription
  Done. Audit row user.plan_changed written (actor "staff script").
  ```

  In the API image the backend is at `/app` (`cd /app` instead of `cd backend`), and the API's `DATABASE_URL` secret is the database it changes. `--plan` is `trial`, `pro` or `pilot`; `--email` and a non-empty `--reason` are required. It refuses (exit 2, nothing changed) an unknown email, a deleted account, a missing reason or another plan name.
  - `pilot`: unlimited checks plus the tools above that need approved access. Stripe billing only moves accounts between `trial` and `pro`, so it never overwrites `pilot`.
  - `trial`: back to the remaining lifetime allowance; it does not erase usage. An account with an active Pro subscription is set back to `pro` by Stripe's next subscription event (the script says so).
  - `pro`: Pro's monthly allowance needs an active Stripe subscription. Without one the account keeps the free allowance until Stripe records one (the script says so). Use Stripe for paid Pro.
- **More free checks: `users.free_check_grant`** (integer, nullable), with a parameterized database update for the verified account ID or email: the account's lifetime free-check allowance is `max(free_check_grant, tier default)`. It is a total, not a top-up: completed checks never reset, so to give an account that has used 15 checks five more, set it to 20. It has no effect while the account is on an active Pro subscription (Pro uses the monthly allowance) and none on pilot. Setting it back to NULL returns the account to its tier default.

`FREE_CHECKS_WORK` and `FREE_CHECKS_PERSONAL` change the default for every free account at once. Do not change platform roles or organization membership to grant access.

There is no checkout for the pilot plan in this release. The **Request paid access** link opens an email draft to the existing contact address. It neither sends an email automatically nor grants access. Agree the commercial terms separately before setting `pilot` with `set_plan.py`.

## Deployment

Apply Alembic migration `0049_trial_checks` before starting the new API. It creates the durable check ledger and backfills past analyses and cost-only results; a cost result with a matching user/mesh analysis is not counted twice. Existing approved `pilot` users remain unlimited. Deploy the matching web build so its preview, analysis and costing requests share the `X-Part-Check-ID` UUID. The server independently binds the ID to the authenticated user and uploaded filename/bytes; the header grants no authority. A recheck uses a fresh ID; it is a new run of the same file's check and does not count again. The former cap override and rolling-window environment variables no longer control the product allowance.

The migration is additive; leave the table in place if rolling the application back. Do not downgrade/drop the ledger on a live system, because doing so loses the new usage history.

## Interrupted work

Idle previews expire after one hour. Running operations retain their reservations until settled, including after an API crash; elapsed time does not permit uncounted simultaneous compute. If a reservation remains stuck, first verify that its worker/request has stopped and inspect saved results for that account and file. An authorized operator can settle completed work or remove only the failed operation under the same user-row lock used by `finish_check`. Never reset the entire account or refund an operation whose result persisted. Accounting database failures stop admission with 503 rather than allowing unpaid compute.

## Verification

`backend/tests/test_validation_caps.py` exercises real PostgreSQL races, lifetime totals, failure refunds, account isolation, the sample part, the tools on every plan and their free-account ceilings, the remaining paid gates, foreign-key locking and commit failure. `backend/tests/test_free_check_access.py` checks anonymous access to core and legacy compute. Frontend tests verify shared request IDs and preview reuse after remounts. `npm run test:e2e:site-design --prefix frontend` checks the public sample-to-account journey and responsive pages. Paid-feature E2E fixtures explicitly grant the existing entitlement only for disposable example-domain accounts on loopback app/database targets; normal signup remains a free account.
